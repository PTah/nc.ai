# Roadmap NotCursor.ai

Планы за пределами ближайших патчей. Текущий релиз — 0.8.5.0 (`docs/releases/`).

**Статус:** субагенты 0.8.4.0; MCP + автоустановка пресетов 0.8.5.1.

## Ближайшие шаги (зафиксировано после 0.7.2)

### 1. Провайдер и модель на каждый чат — приоритет 1

Причина: самое заметное для пользователя при умеренном объёме работ. Сейчас провайдер один
на приложение (`a.llm` собирается в `app.go` в `refreshProvider`), поэтому чат с DeepSeek и
чат с локальной моделью в одном проекте невозможны без переключения настроек руками.

- [ ] Поля сессии: `ProviderID`, `Model` (в `internal/chatstore`, миграция старых сессий — пусто = «как в настройках»).
- [ ] Фабрика провайдера на прогон: `newProvider(cfg, session.ProviderID, session.Model)` вместо глобального `a.llm`; `refreshProvider` остаётся для дефолтов.
- [ ] Селектор в шапке чата: список провайдеров и моделей (для Local — кнопка «список моделей»), сохранение выбора в сессии.
- [ ] Статус-бар и учёт стоимости берут модель из сессии, а не из настроек.
- [ ] Проверка: два чата с разными провайдерами одновременно; перезапуск приложения сохраняет выбор; Auto-модель Local продолжает работать.

### 2. MCP-серверы — приоритет 2

без правок агента.

- [x] `tools/list` → инструменты с префиксом сервера, включение в общий toolset; `tools/call` с таймаутом.

- [x] Проверка: mock stdio-сервер в `internal/mcp/testdata` + unit-тесты.

#### 2b. Структурный контекст репозитория — после MVP клиента — **пресеты в 0.8.5.0**

Цель: агент меньше блуждает `grep`/`read` по огромным деревьям (типичный провал «не нашёл файл/строку»),
без встраивания тяжёлого анализа в ядро NotCursor.

- [x] Пресеты в Settings → MCP: **code-review-graph**, **CodeGraph Context**, **codebase-memory**, **Cognee**.
- [x] Allowlist tools после «Проверить» (пусто по умолчанию).
- [ ] (опц.) Skill / project rule: «сначала спроси граф/память MCP, потом уже широкий grep».
- [ ] Проверка: на крупном репо агент находит нужный модуль через MCP-граф быстрее, чем чистым `grep`.

#### 2c. Опциональный security-режим — только по желанию пользователя

Не продукт AppSec и не default toolset. Формальный анализ (Semgrep / CodeQL / Joern·codebadger)
подключается **снаружи** через MCP, когда пользователь сам включает сервер.

- [ ] Пресет «Security review»: Semgrep MCP и/или codebadger (Joern), allowlist инструментов.
- [ ] (опц.) Skill + заготовка `SECURITY.md` / чеклист ревью — без тащить CPG в `internal/`.
- [ ] Явно **не** делать: встраивать Joern/CPG/GNN в ядро агента, taint-пайплайн как обязательный шаг прогона.

Справка по мотивам (аудит ≠ coding-агент, гибрид граф+LLM полезен снаружи): обсуждение после
статьи PT / VulnGym — выводы зафиксированы здесь как порядок доработок, не как смена продукта.

### 4. Добивки (по одной, между крупными задачами)

Маппинг strong: Z.ai → `glm-5.3`, OpenRouter → `qwen3-coder:floor`, Qwen → `qwen-max`, Yandex → `qwen3-235b-a22b-fp8` (Local — по желанию later). Точка входа: `internal/agent/escalate.go` (`escalateEnabled` / `strongModel`).
- [ ] Anthropic: сохранять `signature` thinking-блока и отправлять его обратно — тогда extended thinking + tools заработает на прямом API.
- [ ] Показывать в ответе реальную модель, если провайдер подменил роут (ShareLLM и подобные): имя из `resp.Model` вместо конфига.
- [ ] DeepSeek: стабильный префикс промпта для prompt cache (сейчас `prompt_cache_hit/miss` только учитываются).
- [ ] macOS-артефакты релиза (`macos-arm64`, `macos-universal`) — нужен macOS-хост; в 0.7.0–0.7.2 их нет.
- [ ] diff viewer и LSP-подсказки; разнести `frontend/src/App.tsx` на хуки.
- [ ] (опц.) Диагностика стрима «тишина N сек → RST»: при `stream read` / `connection reset` писать, сколько секунд не было данных в SSE до обрыва (чат + `agent.log`). HTTP/2 keepalive и счётчик обрывов уже есть (0.7.5+); это только понятнее сообщение, CDN idle не лечит.

### 5. Переход в другой проект по просьбе — приоритет 4 (план)

Запрос: «Перейди в проект Python-sourse» — программа должна переключиться в другой проект и дальше
работать уже там (запускать решения, общаться). Сейчас не умеет, и по замыслу не может.

**Почему сейчас нет**

- прогон приколот к проекту **сессии**: `app.go:3703-3726` берёт `projKey` из `chats.FindProject(sid)`;
- инструменты пинены к корню на прогон: `app.go:3819-3821` (`a.tools.ForRun(projKey)`); комментарий
  там прямо запрещает менять корень на середине — «switching to another project mid-run must not
  redirect file writes, commands or git»;
- чужой проект для инструментов вне скоупа: `internal/tools/scope_guard.go:75` знает другие корни и
  спрашивает подтверждение, но контекст не переключает;
- тула «переключить проект» в спеке нет; чаты хранятся по проекту (`projectKey()`).

**Вариант A (выбран): переключить → завершить прогон → начать новый в новом проекте**

Инфраструктура переключения уже есть: на `tool_ask` из другого проекта фронт сам делает
`openProject(path)` + `switchSession(sid)` (`frontend/src/App.tsx:3243-3264`). Переиспользуем её.

1. **Тул `switch_project(name)`** (бэкенд):
   - резолв по списку открытых проектов: точный путь → basename (регистронезависимо) → при
     неоднозначности ошибка со списком кандидатов;
   - отказ, если проект на замке (`cfg.IsProjectLocked`);
   - из исходного сообщения вырезается фраза перехода, в новый прогон уходит только остаток задачи;
   - результат — специальный маркер, по которому раннер **завершает текущий прогон** (модель не
     продолжает в старом корне).
2. **Событие `project:switch`** `{project, message, handoff}` — отправляется **после** `done`
   текущего прогона.
3. **Фронт**: `openProject(project)` → создать/выбрать чат → `runAgent(sid, message, [], false, false)`.
   Новый прогон стартует только после завершения старого, иначе гонка и два прогона.
4. **Handoff**: первым сообщением нового прогона — короткая сводка (что просили, что сделано, где
   остановились), чтобы агент продолжал, а не начинал с нуля.

**Риски и митигация**

| Риск | Митигация |
|---|---|
| Зацикливание (новый прогон снова видит «перейди в проект X») | Команда перехода вырезается; тул одноразовый на прогон |
| Два прогона одновременно | `project:switch` уходит после `done`; фронт стартует новый прогон после этого |
| Расхождение UI и бэкенда | Проект открывает фронт через `openProject`, а не бэкенд напрямую |
| Неоднозначное имя | Ошибка со списком кандидатов, вопрос пользователю |
| Проект на замке / не открыт | Отказ с текстом, прогон остаётся на месте |
| Потеря нити разговора | Handoff-сообщение; старый чат остаётся в старом проекте |

**Что не меняется:** привязка прогона к проекту сессии, пиннинг инструментов, `chatstore` по
проектам, scope guard. Изменения аддитивные — ломать текущую логику не требуется.

**Порядок работ**

- [ ] Тул `switch_project` + резолв имени + вырезание команды; unit-тесты: точный путь, basename,
      неоднозначность, замок, «не найден».
- [ ] Маркер завершения прогона из тула + событие `project:switch` после `done`.
- [ ] Обработчик во фронте: openProject → чат → runAgent; проверка, что пользователь в проекте прогона.
- [ ] Handoff-сообщение (сводка из последних сообщений и вызовов инструментов).
- [ ] Проверка: «перейди в X и запусти тесты» — переключение, новый прогон в X, старый чат цел;
      отказ для замка; два проекта с одинаковым basename.

## Этап 5 — Субагенты (вложенные прогоны)

### Зачем

Длинные задачи (чтение десятков файлов, поиск по репозиторию) съедают окно контекста: у локальных моделей окно 8–32k, а системный промпт, правила проекта и инструменты занимают до половины. Субагент переносит «шумную» часть работы в отдельный контекст и возвращает в родительский чат короткую сводку.

### Как это устроено

1. **Инструмент `task`** (родитель → ребёнок):
   - вход: `{description, prompt, tools?[], model?}`;
   - `description` — короткая подпись для UI, `prompt` — задание ребёнку;
   - `tools` по умолчанию read-only: `read_file`, `grep`, `glob`, `list_dir`, `git_diff`;
   - `model` по умолчанию `auto` (для Local — правило Auto/Lite, чтобы не тянуть большую модель);
   - выход: `{summary, files[], steps, tokens}` — в родительские сообщения попадает **только** это.

2. **Вложенный прогон** (`internal/agent/subrun.go`):
   - свой `[]llm.Message`, свой `stallWatch`, своя компрессия истории;
   - системный промпт ребёнка: короткий + проектные правила, если не снята галочка «Не подключать проектные правила»;
   - глубина ровно 1 — ребёнок не может вызвать `task` (без рекурсии);
   - лимит шагов и таймаут; отмена родителя отменяет детей через `context.Context`;
   - слот модели у Ollama/Lemonade один, поэтому дети идут **последовательно** (без параллели на MVP).

3. **События и UI**:
   - события `subrun_start`, `subrun_delta`, `subrun_step`, `subrun_end` с `parentCallId`;
   - в ленте — сворачиваемая карточка «Подагент: `<description>`» с текущим инструментом, счётчиком шагов и итогом;
   - в статус-баре — отдельный счётчик токенов подагентов (в общий или отдельной строкой).

4. **Конфигурация** (Settings → Agent):
   - `subagents.enabled` (по умолчанию выкл. до обкатки);
   - `subagents.defaultTools` = read-only;
   - `subagents.maxSteps` (по умолчанию 12);
   - `subagents.allowWrite` (по умолчанию выкл. — писать может только родитель).

5. **Тесты**:
   - изоляция: родитель не видит сообщений ребёнка, только сводку;
   - фильтр инструментов: `write_file`/`shell` недоступны, пока не разрешены явно;
   - отмена: `ctx.Done()` гасит вложенный прогон;
   - лимиты шагов и отсутствие рекурсии;
   - учёт токенов в общий счётчик.

### Порядок работ

1. [x] `task` + вложенный прогон (последовательно, read-only) — MVP (0.8.4.0).
2. [x] События и карточка подагента в ленте.
3. [x] Конфигурация, лимиты, отмена (через ctx родителя).
4. [x] Выбор модели для ребёнка (`model` / auto + LocalLite у ребёнка).
5. [ ] (Опционально) параллельные подагенты, если сервер умеет несколько слотов.

### Риски и решения

| Риск | Решение |
|------|---------|
| Один слот модели (Ollama, Lemonade) | дети запускаются строго последовательно |
| Сводка теряет детали | обязывать ребёнка возвращать список файлов и цитаты; хранить полный лог во вложенной сессии |
| Рост стоимости у облачных провайдеров | лимит на число подагентов за прогон, дефолт — только для Local/дешёвых моделей |
| Сложность UI | карточка сворачивается и не мешает основной ленте |

### Что уже есть похожего

- Компрессия истории — `internal/agent/compact.go`.
- Auto-выбор модели на шаг (в том числе локальной) — `internal/agent/local_route.go`.
- Повтор хода только с read-инструментами — нюдж в `internal/agent/agent.go`.
