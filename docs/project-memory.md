# Память агента: карта проекта, индекс символов, факты и история чатов

Версия: **0.9.0**. Относится к `internal/projindex`, `internal/projmem`, `internal/history`,
`internal/tools/executor.go`, `internal/agent/agent.go`.

## Что за проблема

Между прогонами у языковой модели нет никакой памяти: в контексте она видит ровно то, что положили
в `messages`. До 0.9.0 туда попадало только дерево имён файлов. По строке `internal/netx/ndis.go`
нельзя понять, что внутри разбор hex от строки Windows NDIS, а по `events.go` — что там переходы
online/offline. Поэтому на каждый вопрос «где это лежит» агент начинал с `grep`, потом читал файлы,
потом искал ещё раз — и так в каждом новом чате.

Теперь у агента четыре источника знаний о проекте. Они разные по цене и по назначению, поэтому
подключаются по очереди, а не «всё сразу в промпт».

| Уровень | Что | Где живёт | Сколько стоит | Инструменты |
|---|---|---|---|---|
| L0 | карта проекта (brief) | промпт, каждое сообщение | ~0.9 КБ на проект | — (просто контекст) |
| L1 | индекс символов | память процесса + файл кэша | 0 (локально), 1 вызов на вопрос | `find_symbol`, `project_search` |
| L2 | факты проекта | config-каталог ОС | ~1.2 КБ в промпте + вызовы | `remember`, `recall`, `forget` |
| L3 | история чатов | `chatstore` (уже был) | 0 в промпте, 1 вызов на вопрос | `history_search` |

## L0 — карта проекта в промпте

Второе сообщение после system prompt — `<project_map>`. Оно начинается с brief, ниже идёт прежнее
дерево путей в `<workspace_tree>`.

Пример (сокращённо, реальный вывод на этом репозитории):

```text
root: nc.ai · go notcursor.ai/app · 338 files · 54.9k lines · 3207 symbols
go: 36 packages · internal/agent(agent,30f), root(main,5f), internal/config(config,8f),
    internal/tools(tools,15f), internal/workspace(workspace,9f), internal/llm(llm,17f), +30 more
entry: cmd/checkconnect/main.go, cmd/migratechat/main.go, internal/mcp/testdata/mock_server.go, main.go
big: frontend/src/App.tsx 8879L, app.go 4322L, internal/config/store.go 2005L, internal/agent/agent.go 1615L
code: frontend/src 9, . 4, scripts 4 · ts×7 tsx×6 sh×4 ps1×3 js×2 py×1
docs: 90 md · docs 89, README.md
index: find_symbol(name) / project_search(query) search these symbols — one call instead of grep→read_file loops
```

Что попадает в brief:

- корень, go-модуль (из `go.mod`), число файлов / строк / символов;
- go-пакеты по объёму — видно, где сосредоточен код;
- точки входа: `package main` с `func main` и `cmd/*/main.*`;
- крупнейшие файлы (> 40 строк) — «где мясо»;
- не-Go код по каталогам и языкам, документация по каталогам.

Бюджет: **1600 байт** на облачных моделях, **700** на локальных (`LocalLite`). Обрезка идёт по
границе строки — половина фразы в промпте только путает модель. Лимиты заданы в `app.go`
(`briefBudget`) и `internal/projindex/brief.go`.

## L1 — индекс символов проекта

Пакет `internal/projindex`: детерминированный обход проекта, без LLM и без внешних сервисов.

| Язык | Как разбирается | Что попадает |
|---|---|---|
| Go | `go/parser` + `go/ast` | функции, методы с приёмником (`*Manager`), типы, `struct`/`interface`, `const`/`var`, первая строка doc-комментария, `file:line` |
| TS/TSX/JS/JSX/Vue/Svelte | regex | `function`, `const x = () =>`, `const x = function`, `class`/`interface`/`enum`/`type` |
| Python | regex | `def`, `async def`, `class` |
| C# | regex | `class`/`record`/`struct`/`interface`/`enum`, методы с модификаторами |
| PowerShell | regex | `function Verb-Noun` |
| sh/bash/zsh | regex | `function name`, `name() {` |
| Rust | regex | `fn`, `struct`/`enum`/`trait`/`mod` |
| Java/Kotlin/Scala/Groovy | regex | `class`/`interface`/`enum`/`object`, `fun` |
| Ruby | regex | `def`, `class`/`module` |

Комментарий над объявлением (до двух строк) сохраняется как описание символа — именно он потом
отвечает на вопрос «где обработка online/offline», даже если в имени этого нет.

### Что не индексируется

- каталоги `node_modules`, `vendor`, `dist`, `build`, `out`, `target`, `obj`, `bin`, `coverage`,
  `.git` и любые каталоги, начинающиеся с точки;
- бинарники и архивы (`*.exe`, `*.dll`, `*.png`, `*.wav`, `*.zip`, …);
- файлы больше 1 МБ (минифицированные бандлы, дампы) — они остаются в списке файлов, но не парсятся;
- на очень больших репозиториях парсинг ограничен 5000 файлов за первый проход.

### Кэш и инкрементальность

- ключ актуальности файла — **размер + mtime**; изменился один файл — перепарсивается только он;
- индекс лежит в памяти процесса и дублируется на диск, чтобы перезапуск приложения не парсил
  проект заново;
- версия кэша (`cacheVersion` в `internal/projindex/index.go`) сбрасывает весь кэш при изменении
  экстрактора.

Пути:

| ОС | Файлы индекса |
|---|---|
| Windows | `%LOCALAPPDATA%\nc.ai\projindex\<hash>.json` |
| macOS | `~/Library/Caches/nc.ai/projindex/<hash>.json` |
| Linux | `~/.cache/nc.ai/projindex/<hash>.json` |

### Инструменты

```text
find_symbol(name: "ProjectTree", path?: "internal/", limit?: 25)
```

Подстрока по имени (регистр не важен), а если в шаблоне есть метасимволы regex — сам шаблон.
Сортировка: точное имя → префикс → вхождение → короткое имя. Вывод:

```text
func ProjectTree — internal/workspace/tree.go:13 · builds a compact directory map (names only)
method (*Manager) ProjectTree — internal/workspace/manager.go:213 · …
```

```text
project_search(query: "online offline event", path?, limit?)
```

Скоринг по трём полям: имя символа, doc-комментарий, путь файла. Возвращает символы, а затем файлы
(`file … · 8879L · 214 symbols`) — если совпадение только в пути.

Оба инструмента доступны в наборах read-only, explore, lite и у субагентов: они ничего не меняют на
диске и спокойно идут параллельно.

## L2 — факты проекта (долгая память)

Пакет `internal/projmem`. Заметка — это **одна строка факта** плюс пути, к которым она относится.

```text
remember(
  text: "Порт монитора = hex от строки Windows NDIS, разбор в ndis.go",
  refs: ["internal/netx/ndis.go", "internal/netx/events.go"],
)
```

Что происходит дальше:

1. Заметка нормализуется (пробелы, регистр, хвостовая пунктуация) и получает короткий id.
2. Если такой факт уже есть — обновляется: текст заменяется, пути сливаются, дата обновляется.
   Копии не плодятся, даже если писать одну и ту же мысль каждый день.
3. На старте следующего прогона заметки попадают в промпт блоком `<project_memory>`.

```text
<project_memory>
- Порт монитора = hex от строки Windows NDIS, разбор в ndis.go (internal/netx/ndis.go, internal/netx/events.go)
- Сборка exe: build.ps1, артефакт build/bin (build.ps1)
</project_memory>
```

### Протухание — главная деталь

Память не выдаётся за истину. Если файл из `refs` изменён **после** записи заметки, `recall` и блок
в промпте помечают её:

```text
- Порт монитора = hex от строки Windows NDIS (internal/netx/ndis.go) — файл изменён после записи, проверь
```

То есть агент знает, где искать, но обязан перечитать изменившийся файл, прежде чем утверждать.
Это дешёвая замена «доверяй памяти на слово» и «не доверяй памяти вообще».

### Ограничения

- лимит **300** заметок на проект, при переполнении вытесняются самые старые по дате обновления;
- одна заметка — до 400 символов, до 6 путей;
- память привязана к **абсолютному пути** проекта: перенесли папку — память осталась по старому пути
  (заметки можно перенести руками, см. «Сброс» ниже);
- `forget(id)` удаляет заметку, id показывает `recall`.

Пути:

| ОС | Файлы памяти |
|---|---|
| Windows | `%APPDATA%\nc.ai\project-memory\<hash>.json` |
| macOS | `~/Library/Application Support/nc.ai/project-memory/<hash>.json` |
| Linux | `~/.config/nc.ai/project-memory/<hash>.json` |

Память специально живёт **вне репозитория**: она не попадает в git, не конфликтует при rebase и
работает на проектах, куда у приложения нет прав записи.

### Как писать полезные заметки

| Хорошо | Плохо |
|---|---|
| «Порт = hex от строки NDIS, разбор в `ndis.go`» + пути | «Разобрался с портом» |
| «Таймаут шага считается в `agent/stall.go`, порог 90 с» + путь | «Про таймауты смотри где-то в агенте» |
| «Решение: не тянем LSP в 0.9, причин две — …» + ссылка на обсуждение | «Не делаем LSP» без причины |

Правило: заметка должна экономить следующий поиск, а не пересказывать переписку.

## L3 — история чатов проекта

Пакет `internal/history`, инструмент `history_search`. Ищет по сообщениям user/assistant в живых и
архивных чатах **текущего проекта** — чужие переписки в выдачу не попадают.

```text
history_search(query: "hex NDIS порт", limit: 8)
```

```text
· 2026-10-26 «разбор NetLynx» · assistant · 3f2a91c4
  …Порт — это hex от строки Windows NDIS, парсится в internal/netx/ndis.go…
```

Как считается релевантность: токены запроса (слова от 3 символов) по вхождениям с потолком,
бонус за точную фразу, бонус за совпадение в названии чата, небольшой бонус строке пользователя.
Не больше **двух** хитов на чат, снипет ±180 символов вокруг первого совпадения, обрезка по границе
UTF-8.

Вызов стоит один шаг и заменяет попытку «вспомнить» решение, которое принималось в прошлом чате.

## Как это выглядит в работе

Вопрос «где в проекте считается порт монитора?» в новом чате теперь идёт так:

1. brief уже в промпте — агент знает, что есть каталог `internal/netx`;
2. `project_search("порт монитора ndis")` → `internal/netx/ndis.go:120`;
3. `read_file("internal/netx/ndis.go", 100, 140)` — проверка перед утверждением;
4. `remember("Порт = hex от строки NDIS…", ["internal/netx/ndis.go"])` — чтобы в следующий раз
   хватило шага 1.

Вместо: `grep` → 3 × `read_file` → ещё один `grep` — и то же самое в следующем чате.

## Сброс и обслуживание

Индекс (пересоберётся сам, безопасно):

```powershell
# Windows
Remove-Item -Recurse -Force "$env:LOCALAPPDATA\nc.ai\projindex"
```

```bash
# macOS / Linux
rm -rf ~/Library/Caches/nc.ai/projindex 2>/dev/null || rm -rf ~/.cache/nc.ai/projindex
```

Память проекта:

```powershell
# Windows — стереть всю память всех проектов
Remove-Item -Recurse -Force "$env:APPDATA\nc.ai\project-memory"
```

```bash
# macOS / Linux
rm -rf ~/Library/Application\ Support/nc.ai/project-memory
rm -rf ~/.config/nc.ai/project-memory
```

Точечно — через `forget(id)`: не удаляйте JSON руками, приложение держит его же в памяти процесса.
После правки файлов памяти на диске перезапустите приложение.

## Проверка, что работает

1. Откройте проект и спросите в чате: «где лежит обработка X?».
2. В ленте должен появиться `find_symbol` или `project_search`, а не цепочка `grep`.
3. Попросите: «запомни: <факт> (путь)» — агент вызовет `remember`.
4. Новый чат в том же проекте: факт должен быть в контексте без напоминания — проверяется вопросом
   «что ты уже знаешь об этом проекте?».
5. Поменяйте файл из `refs` и снова спросите — заметка должна прийти с пометкой «файл изменён
   после записи, проверь».

## Чего это не заменяет

- **MCP-граф кода** (`codebase-memory`) остаётся полезным для межфайловых связей «кто вызывает кого»
  на больших базах: локальный индекс отвечает «где объявлено», а не «какие 12 мест это вызывают»;
- **актуальность**: агент всё равно читает файл перед правкой — индекс и память экономят поиск, а не
  отменяют проверку;
- **`grep` по содержимому**: если нужен произвольный текст (сообщение об ошибке, строка в JSON),
  индекс промахнётся, и это нормальный сценарий — `grep` остаётся в наборе.
